# Bazel

Scope: how the build is wired, in every language. Audience: anyone
touching `MODULE.bazel`, `.bazelrc`, a `.bzl` file or a BUILD file.
Prerequisite: layout.md.

The build is bzlmod-only, hermetic where the platform allows it, and
every check a language has runs as a Bazel target, so `bazel build //...`
and `bazel test //...` are the whole gate (gates.md).

## BZ-1. One module, bzlmod, no WORKSPACE

`MODULE.bazel` declares every ruleset and toolchain. `MODULE.bazel.lock`
is committed. `.bazelversion` pins Bazel for bazelisk, and bazelisk is the
only thing a fresh machine installs.

**Rejected.** A launcher that wraps Bazel with its own configuration
language and a second version pin, while still running Bazel underneath.
bazelisk plus `.bazelversion` does the one job needed.

## BZ-2. Common flags come from a generated preset

`tools/preset.bazelrc` is generated by bazelrc-preset.bzl for the Bazel
version in `.bazelversion` and imported at the top of `.bazelrc`. It is
checked in and reviewed like any other file; regenerate it after a Bazel
upgrade with `bazel run //tools:preset.update`. Repository policy (lint
flags, coverage filters, the platform output directory) stays in
`.bazelrc` itself, below the import. Machine-local overrides go in
`user.bazelrc`, which is gitignored and imported last.

The preset defines a `ci` configuration (`--config=ci`: lockfile mode
error, terse output, retries), which is what a continuous-integration job
passes. Nothing else in the repository knows about CI.

## BZ-3. Toolchains are pinned and fetched, never taken from the host

The C toolchain is clang from toolchains_llvm with a pinned sysroot per
Linux target, and it is part of the core whether or not the repository
has Rust: Rust links with it, and the format entry point's launcher needs
a C toolchain to resolve at all. Rust comes from rules_rust with an exact
version. Python comes from python-build-standalone through rules_py, with
uv as the resolver. Node and pnpm come from rules_nodejs and rules_js.
Each is a pin in `MODULE.bazel` (dependencies.md).

**Why.** A fresh Linux machine needs only Bazel; the first build downloads
everything else. The claim is weaker on macOS, where the Rust link uses
the host SDK, so that machine also needs the Xcode Command Line Tools.
Windows hosts are unsupported.

**Consequence.** The first build on a fresh machine is slow. Changing a
build setting (a lint flag) discards the analysis cache; expect one slow
build after editing policy.

## BZ-4. Language rules are loaded from the repository's wrappers

Every BUILD file loads `rust_library`, `rust_test` and `rust_binary` from
`//tools/rust:defs.bzl`, `py_library`, `py_test` and `py_binary` from
`//tools/python:defs.bzl`, and `ts_library`, `ts_test` and `vite_app`
from `//tools/typescript:defs.bzl`. Nothing loads rules_rust, rules_py,
rules_js or rules_ts directly, except the wrappers themselves and the
generated-code rules (proto.md).

Each wrapper is a Bazel symbolic macro over the ruleset's rule of the same
name. Beside the rule target it declares the checks over exactly that
target's sources: clippy and rustfmt for Rust; ruff, the format test and
mypy for Python; the type check, ESLint and Prettier for TypeScript. The
generated targets are visible to the calling package and inside the
wrapper only. `bazel build //...` builds the build-time checks and
`bazel test //...` runs the test-time ones, so no BUILD file ever names a
lint target.

**Why.** A file is linted by the target that owns it, so no second file
list exists to drift. Before the wrappers, each crate declared four
targets by hand and the rule that clippy must list the test target was
held only by a scaffolding skill; crates with integration tests listed
those in two places and the lists drifted.

**Rejected.**
- One combined library-plus-tests macro: a library and its tests need
  different visibility and dependencies, and a merged declaration is not
  the shape Bazel users expect. Two declarations per package, each
  linting its own sources, give the same guarantee.
- Lint aspects enabled in `.bazelrc` as the gate: an aspect cannot
  analyze a Python library that the uv hub makes incompatible outside a
  venv-configured target, so `bazel build //...` would skip it. Per-target
  tests reach every line. The aspects exist as whole-tree escape hatches
  (`--config=clippy`, `--config=rustfmt`, `--config=ruff`,
  `--config=eslint`), off by default because they slow local iteration.
- A per-target lint configuration attribute: one a new BUILD file omits
  is silently unenforced. Global flags cannot be forgotten.

**Mechanics the wrappers fix.** Symbolic macros cannot glob, so
`glob(["*.rs"])` stays at the call site, and never `glob(["**/*.rs"])`:
subdirectories are their own packages and a recursive glob would cross
the boundary. Every list attribute is `configurable = False`; the one
configurable attribute is `target_compatible_with`, for tests that run
only on hosts with a pinned service archive (testing.md). A `testutil/`
package's library must say `testonly = True`; the Rust wrapper refuses
one that does not, so the rule that production code cannot depend on
test helpers is checked at load time.

## BZ-5. One formatter entry point

`bazel run //:format -- <files>` rewrites files of every language the
repository builds (ruff, rustfmt, buildifier, Prettier) through
rules_lint's `format_multirun`; with no arguments it formats the tracked
and modified files under the current directory. `bazel run //:buildifier`
also applies buildifier's lint fixes, which the entry point does not. The
agent-harness edit hook runs both.

`rustfmt.toml` at the root carries the Rust edition because upstream
rustfmt, which the entry point runs, is not told it on the command line
the way rules_rust's own targets are; keep it in step with
`rust.toolchain(edition = ...)`.

## BZ-6. Mechanical BUILD edits go through buildozer

Adding a dependency or renaming a target is a buildozer command, not a
text edit:

    bazel run @buildozer -- 'add deps //rust/hello/greeting:hello_greeting' //rust/hello/app:hello_app

## BZ-7. The output directory is per platform

`--experimental_platform_in_output_dir` keeps outputs in a
platform-specific directory, so switching target platforms (a container
image's Linux binary, built on macOS) does not wipe and rebuild
everything.

## BZ-8. Telemetry is off

`--repo_env=DO_NOT_TRACK=1` opts out of the usage reports Aspect's
rulesets send. Nothing about the repository leaves the machine without a
decision.

## BZ-9. Generated files are never checked in, except lockfiles and the preset

Proto codegen runs at build time (proto.md). The exceptions are files a
tool regenerates from a pin and a review wants to see diffed: the three
lockfiles, `tools/preset.bazelrc`, and any golden file a test compares
against. Each has a documented regeneration command (dependencies.md).
