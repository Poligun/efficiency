## Before you merge

**reqwest 0.13.0 is a breaking change.** Under Cargo's semver rules for `0.x` crates, a bump in the minor position is a major bump — `0.12` and `0.13` are incompatible. Three things follow from that:

1. Read the reqwest 0.13 changelog for the API you actually use, and confirm the crate still builds. A dependency-only diff gives a reviewer no signal about this; only `cargo build` and the test suite do.
2. Check whether any other dependency in the tree also depends on `reqwest 0.12`. If one does, Cargo will link both versions, and any type that crosses the boundary — `reqwest::Client`, `Url`, `Error`, a middleware trait — will fail to unify. That failure shows up as a confusing type mismatch, not as a version error.
3. If this crate is itself a library and re-exports anything from reqwest in its public API, then `reqwest 0.13` makes **this crate's** next release breaking too. `version = "0.3.1"` in `Cargo.toml` is unchanged on this branch, which is fine for a merge but is a decision to make at release time.

**One sanity check on the lockfile.** `Cargo.toml` bumps `tracing` to 0.1.41, but `Cargo.lock` has no `tracing` entry at all. That may be an artifact of how the lockfile is maintained here, but it's worth confirming the lock was regenerated by a real `cargo update` rather than hand-edited — a hand-edited lockfile can pin a version the resolver would never have chosen.
