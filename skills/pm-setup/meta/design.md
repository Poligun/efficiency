# pm-setup — design

> Status: **confirmed**. Produced during a grilling session on 2026-08-20 (15
> questions, all answered by the user). Companion skill: `project-manager`.

## What this is

The day-0 half of a transferrable issue-management system. One run deploys, into
a target repository: the five-family label taxonomy from the originating repo's
ADR, the vocabulary doc, an adoption ADR, the PR template, an AGENTS.md pointer,
and — the load-bearing piece — the **tracker seam file** at `.claude/tracker.md`.

The one-sentence architecture: **skills consume operations, not backends**. No
consuming skill (spec, ticket, or `project-manager`) ever hardcodes `gh` or any
tracker's API; they read the seam file, which states — in prose plus concrete
commands — how to perform a fixed vocabulary of operations against *this* repo's
tracker. Swapping GitHub for Jira is writing a new seam file, not touching any
skill.

## Why a two-skill split

Deployment and operation have different cadences: `pm-setup` runs once per repo
(re-runs are diffed refreshes); `project-manager` runs daily. A monolith would
couple a rarely-exercised interview to a frequently-exercised audit. The third
leg — spec/ticket lifecycle skills — is deliberately **not** part of the
package (see decisions.md: upstream skills stay upstream).

## The seam

Fixed operation names, per-backend implementations, declared constraints:

- **Identity** — backend kind, repo/project, where the vocabulary lives.
- **Vocabulary mapping** — how type/priority/status/resolution are carried. On
  GitHub all four are labels (GitHub lacks the native concepts). On Jira most
  are native fields — the label taxonomy exists *because* GitHub lacks them, so
  a Jira deployment is chiefly a mapping, not a label deployment.
- **Operations** — `create-issue`, `rewrite-issue`, `transition-status`,
  `close-with-resolution`, `link-parent`, `link-blocker`, `find-work`,
  `pr-linkage`. Names are frozen; consuming skills address operations by name.
- **Transition constraints** — per-transition required fields. Empty on GitHub;
  on Jira, filled by live discovery of the actual project's workflow (different
  projects have different state machines and demands).
- **Pass-through fields** — corp fields outside the taxonomy (sprint, story
  points, due date): recorded with *when* they are demanded, prompted for at
  those moments, never absorbed into the core taxonomy.
- **For lifecycle skills** — explicit stamping instructions that override
  upstream skills' generic defaults (notably `ready-for-agent`).

The seam file is **generated by discovery, not stamped from a static copy**: on
GitHub the delta is repo identity, areas, and doc paths; on Jira the discovery
step inspects the live project via whatever MCP/CLI exists.

## Canonicality and drift

The templates in `templates/` are the master. Each deployed repo owns its
generated copies outright; there is no sync obligation in either direction, and
drift between repos is deliberate — each repo's adoption ADR records its own
answers. The originating repo itself becomes just another deployed copy (its
`issues.md` was the source the template was extracted from; regenerating it
from the template proves round-tripping).

## The tiered interview

Impose the universal core (type/priority/status/resolution, palette,
invariants, state machines, PR conventions); ask at most three questions — the
`area/*` set (proposed from repo structure), the doc layout (defaulting to the
standard one), and the PR template (consolidate with an existing one, create,
or skip — the linkage conventions are core, the template *file* is optional).
Deviations the user requests are recorded in the generated ADR rather than
blocked. This sits between "impose everything" (breaks on repos
with existing doc conventions) and "interview everything" (a 20-question slog
that defeats easy transfer).

## Rollout state

- Round 1 (this): GitHub backend, `pm-setup` + `project-manager`, first
  consumer is the `efficiency` repo itself.
- Round 2 (deferred): Jira/Confluence/Slack seam implementations (needs a live
  corp instance), plugin packaging as the corp distribution vehicle.
- Stays local to the originating repo, tracked there as a follow-up: Projects
  v2 board / milestones — GitHub-specific furniture that would pollute the seam.
